# alembic

## Purpose
Alembic migration environment and revision history for the Postgres schema
defined by `aicom.store.models`. Two revisions exist so far, tracking the
initial schema and one additive column.

## Key Files
| File | Description |
|------|-------------|
| `env.py` | Migration runtime config; wires `Base.metadata` as autogenerate target and sets the DB URL from app settings. |
| `script.py.mako` | Template used by `alembic revision --autogenerate` to generate new revision files. |
| `versions/0001_initial.py` | Initial schema: `agent`, `system_state`, `task`, `run`, `approval`, `artifact`, `event`, `spend_ledger` tables plus their indexes/FKs. Revision `d7d59d6924a4`. |
| `versions/0002_agent_gated_tools.py` | Adds `agent.gated_tools` (Postgres array, `NOT NULL DEFAULT '{}'`). Revision `b41c7f0a9e12`, down-revision `d7d59d6924a4`. |

## For AI Agents

### Working In This Directory
- `env.py` does **not** read the DB URL from `alembic.ini`. It calls
  `load_settings().database_url` from `aicom.config` and sets it via
  `config.set_main_option("sqlalchemy.url", ...)` at import time (line 21).
  So the URL alembic uses is whatever the app's settings resolve to (env
  vars / `.env`), not a static `sqlalchemy.url` line in `alembic.ini`.
- `target_metadata = Base.metadata` from `aicom.store.models`, so
  `alembic revision --autogenerate` diffs against the live ORM models.
- **Critical**: the test suite does NOT run these migrations. `tests/store/conftest.py`
  builds the schema directly with `Base.metadata.create_all(eng)`. This means
  a model change alone will pass every test while leaving production schema
  stale (and the reverse: a hand-written migration that drifts from the model
  will never be caught by pytest). Any change to `aicom.store.models` needs
  BOTH the model edit AND a new revision in `versions/`, or prod and tests
  will silently diverge.

### Testing Requirements
- Generate a new revision after a model change:
  `.venv/bin/alembic revision --autogenerate -m "description"`
- Review the generated file — autogenerate comments explicitly say "please
  adjust" (see `0001_initial.py` line 24); it does not always infer
  server_default/nullability intent correctly (0002 hand-adds a
  `server_default` so existing rows get `'{}'` instead of `NULL`, since
  `gated_tools` is treated as a denylist that must never be `NULL`).
- Apply to a real database: `.venv/bin/alembic upgrade head`
- There is no automated check that models and migrations match; verify by
  eye or by running `alembic upgrade head` against a scratch DB and diffing
  against `Base.metadata.create_all`.

### Common Patterns
- Revision IDs are opaque hashes generated by alembic, chained via
  `down_revision`; `versions/0001_initial.py` has `down_revision = None`.
- Every migration defines both `upgrade()` and `downgrade()`.

## Dependencies

### Internal
- `aicom.config.load_settings` (DB URL)
- `aicom.store.models.Base` (autogenerate target metadata)

### External
- `alembic`, `sqlalchemy`, Postgres (`postgresql.ARRAY`, `postgresql.JSONB` dialect types used in versions)
